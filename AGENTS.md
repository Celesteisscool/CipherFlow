# AGENTS.md — how to work in this repo

Read this before touching anything. It exists because an agent repeatedly did work nobody
asked for and ignored direct instructions. Every rule below is a response to a specific
past failure, named so it is recognisable when it starts happening again.

## The project

A single-file, offline node-based CyberChef editor. `index.html` at the repo root is the
whole shipped app (engine inlined, ~14 MB, served by GitHub Pages from `/`). The readable
sources are `dev/app.js` (canvas, nodes, wiring, run loop) and `dev/styles.css`.
Recreated dCode/CacheSleuth operations live in `dev/dcode/`.

## Edit sources, never the built file

`index.html` is generated by `dev/build.mjs`. Never hand-edit it — edit `dev/app.js` or
`dev/styles.css`, then rebuild. A change that alters shipped behaviour is committed as
**source + rebuilt `index.html` in the same commit**; leaving `index.html` stale means the
deployed site does not have the fix.

Build requires two generated inputs that are not committed (`dev/modules/modules/*.js`,
`/tmp/chefworker.js`). Generate them once:

```bash
npm install
node dev/collect-entry.mjs   # -> dev/cc-tests.json
node dev/gen-meta.mjs        # -> dev/meta.json, dev/testplan.json
node dev/build.mjs           # -> index.html
```

There is no test suite. `npm test` is a stub that exits 1 — do not run it, do not fix it
unless asked.

## "Push" means push

When the user says push, publish, or ship: run `git status`, `git diff`, stage the relevant
files, commit, push. That is the entire task. Do not open an investigation first, do not
act on a hypothesis you were mid-way through, do not run checks the request did not imply.
This rule exists because "push!" was answered with eight code searches about an unrelated
rendering bug.

## Do one task, then stop

One instruction = one task. When it is done, report and stop. Do not chain into adjacent
improvements, refactors, or "while I'm here" fixes. If you notice a real bug outside the
request, say so in one sentence and let the user decide.

Precedent: "work on the magic function" turned into profiling the Aperisolve graph and
re-encoding bit planes as 1-bit PNGs. The user had not asked for performance work at all.
Read the request literally.

## Verification: the minimum that proves the change

Scale it to the change, and stop when it is proven:

- edited JS: `node --check dev/app.js`
- edited operation/runtime modules: `node --check` on the touched file
- anything that ships: rebuild, confirm the build exited 0
- behaviour change: one targeted check of that behaviour (serve with
  `node dev/serve.mjs 8788` and inspect the actual case)

That is the ceiling, not the floor. Do **not** build benchmark cards, 19-case suites,
multi-step UI walkthroughs, or fresh test harnesses for a one-line fix. Re-running a suite
that already passed on unchanged code is waste. Report what you ran and what you could not
run; never call a compile a behaviour test.

## No unrequested artifacts

Do not create these unless the user asks for them:

- files in `reports/` or `screenshots/`
- temporary loader pages, probe files, or debug HTML (if one is unavoidable, delete it
  before finishing — leaving `dev/_loadgraph.html` behind was a mistake)
- benchmark or self-test UI inside the app
- new markdown docs

Graph JSONs at the repo root and anything in `reports/`/`screenshots/` stay local and
untracked unless explicitly told to commit them.

## Ask clarifying questions up front

If a request is ambiguous, or could be read more than one way, ask everything you need to
know **before starting** — in one batch, not one question per turn — then wait for the
answer. Settling the scope in a single exchange is much cheaper than starting on a guess
and reworking it, and it is the direct fix for "work on the magic function" turning into
unrelated profiling work.

- Ask all the structural questions at once: what is in scope, which node or screen is
  affected, what the finished behaviour should look like.
- Do not start the task, or any adjacent work, in the same turn as the question. Starting
  while an answer is outstanding is how the wrong thing gets built.
- Do not fire unrelated tool calls to look busy while waiting.
- Check first whether the repo, this file, the README, or the conversation already answers
  it; reuse that answer instead of asking again.
- A clear, specific instruction is not an invitation to interview the user. Start on it.

## Do not carry an agenda across messages

A new user message replaces your plan; it does not append to it. If you were mid-hypothesis
when the message arrived, drop the hypothesis. The most common failure in this repo has
been an in-flight idea being treated as a standing requirement, which makes a one-line
request look like an hour of unrelated activity.

## Report honestly

Say what changed, which files, what you ran and what it returned. If you did not verify
something, say it was not verified. Do not describe a compile as a behaviour check, and do
not describe a pushed commit as a deployed site.
